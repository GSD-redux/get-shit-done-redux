**`progress.percent` now moves as plans complete inside the current phase, and never moves backward when a phase gains plans** — the milestone percent is composed per phase (a closed phase fills its slot, an open phase fills it by its own summarized/plans fraction, an open phase with no plan files fills nothing) instead of capping the whole milestone by the completed-phase count with `min(plan_fraction, phase_fraction)`. Under the cap, the bar sat at a constant for the whole of every phase once its plan fraction overtook the phase count — `percent: 67` beside `completed_plans: 39, total_plans: 39` — and dropped when gap-closure plans were added to an in-flight phase. The no-false-100% guarantee the cap served is kept: unrealized future phases still contribute nothing (they carry no passing `*-VERIFICATION.md`, so they are never counted complete), and a milestone with any phase still open reads at most 99. `state json`, `state sync`, `state update-progress` and the STATE.md body bar all apply the same composition to the phase set each is given. (They can still report different numbers where their phase sets differ: `buildStateFrontmatter` de-duplicates directories that normalize to the same phase number per #2445/#3355 and `cmdStateSync` does not — a pre-existing asymmetry that reproduces on the base commit and is untouched here.)
