**The commit-message hook no longer blocks every heredoc-form commit** — with `hooks.community: true`, `gsd-validate-commit.sh` rejected `git commit -m "$(cat <<'EOF' … EOF)"` with `CONVENTIONAL_COMMITS_VIOLATION` no matter what the message said, because its extraction regex `-m[[:space:]]+"([^"]+)"` matched ACROSS NEWLINES: bash `[^"]` includes them, so the capture ran from the quote after `-m` all the way to the final quote at `)"`, and `head -1` returned the literal `$(cat <<'EOF'` as the subject. That is Claude Code's own documented commit idiom, so enabling the toggle — which also carries the useful session-state and phase-boundary hooks — made every multi-line commit fail deterministically. Extraction now goes through a new `extractCommitSubject()` in `hooks/lib/git-cmd.js`, walking tokens from the subcommand on the same shared scanner the module's `isGitSubcommand()` classifier already uses, and resolving a command-substituted heredoc to its body's first line. Both directions are pinned: a conforming heredoc message passes, a non-conforming one is still blocked, and the 72-character subject check now measures the resolved subject rather than the opener. Because the walk starts at the subcommand, `git -C <path> commit` and env-prefixed invocations extract correctly too — forms the raw string scan never handled. Deliberately unchanged: a glued `-mfeat: x` and `--message=…` still yield no message, exactly as the regex left them, so the fix stays scoped to the reported defect. (#3802)
