**The commit-message hook no longer blocks every heredoc-form commit** — with `hooks.community: true`, `gsd-validate-commit.sh` rejected `git commit -m "$(cat <<'EOF' … EOF)"` with `CONVENTIONAL_COMMITS_VIOLATION` whatever the message said, because its `-m` capture regex `-m[[:space:]]+"([^"]+)"` matched ACROSS NEWLINES: bash `[^"]` includes them, so the capture ran from the quote after `-m` to the final quote at `)"`, and the message's first line was the literal `$(cat <<'EOF'`. Ordinary multi-line messages were never affected — `-m "fix: subject\n\nbody"` validated correctly all along; the deterministic failure was specific to the command-substituted heredoc opener. That opener is Claude Code's own documented commit idiom, so enabling the toggle — which also carries the useful session-state and phase-boundary hooks — made that pattern fail every time. The subject is now resolved through `resolveCommitSubject()` in `hooks/lib/git-cmd.js`, a pure string helper that maps an already-selected `-m` argument to the line that should be validated, handling the opener spellings bash accepts (`<<TAG`, `<< TAG`, quoted tags, non-identifier tags such as `END-MSG`, a path-qualified `cat`) and stripping the leading tabs `<<-` strips. **Which** argument counts as the message is deliberately unchanged, so no command starts or stops being validated: `git commit -- -m WIP`, `git commit --amend && echo -m WIP`, `-m "" --allow-empty-message` and unquoted `-m WIP` all behave exactly as before, each pinned by a differential test. Recognition is anchored to a command substitution at both ends, so a message that merely contains — or ends in — `<<WORD` is not mistaken for an opener; without that anchor, `-m "WIP notes <<EOF\nfix: smuggled subject"` would resolve past the real subject and allow a non-conforming commit. Both directions are pinned per opener spelling: a conforming body passes, a non-conforming one is still blocked, and the 72-character check measures the resolved subject. Known limitation, unchanged: a double-quoted heredoc tag nested inside the double-quoted argument (`-m "$(cat <<-"TAG"…)"`) still truncates the capture and is blocked, exactly as before. (#3802)
