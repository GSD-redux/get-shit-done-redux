**Projects using the bracket phase-ID convention now have their ROADMAP read correctly** — `roadmap analyze`/`get-phase`, the W005/W006/W007 phase checks, `validate health`, and both `total_phases` derivations previously matched only the `Phase N:` spelling and the `NN-name` directory shape, so on a bracket project every phase was invisible: `phase_count` and `total_phases` fell back to the on-disk directory count, `get-phase` reported not-found, every `GSD.02-05-slug` directory was reported malformed, and a completed milestone was warned to have unstarted phases. Milestone scoping now also recognises the ADR-canonical `## [GSD.02] Foundation` heading — including the version-less form, with no `vN.N` and no status emoji — at any milestone heading level (`#` through `###`, the same ceiling the selector and `isMilestoneBounded` already use) and across a milestone split over two headings, with the version-bearing heading in EITHER position (a checklist/overview section followed by a later `(Phase Details)` section, or the reverse) — and applies to the phase DIRECTORIES too, so a bracket project's `completed_phases`, `total_plans`, `completed_plans` and progress percent are counted from ALL of the phases of the milestone STATE.md asserts, not a subset — with one narrow exception scoped to `total_phases`/`phase_count` only (the phase-0 directory is still admitted into `completed_phases` either way): a bracket-SPELLED bare `0`/`0.x` phase token (e.g. `### [GSD.02] 0:`) keeps `roadmap analyze`'s own pre-existing sentinel reading, base-identical rather than newly introduced; the LEGACY-spelled form (`### Phase 0:`) in a bracket repo IS counted — the mid-migration guard this PR adds — rather than from every directory on disk, on both the version-bearing and version-less heading forms; phase-heading counting itself accepts only CommonMark-correct ATX headings — level 2 through 4, with at least one space after the hashes — so a level-5 heading or a space-less `###[GSD.02]` heading is not counted, the same cap and grammar `getMilestonePhaseFilter`'s own phase scan already enforces (the milestone-BOUNDARY machinery — the selector, `isMilestoneBounded`, the preamble scan — caps at `###` instead); a prior or later sibling milestone's directories are excluded either way, at any of those heading levels or split shapes, and an unrelated bracket-shaped heading with no phase children of its own (e.g. a prose cross-reference like `## [ADR.612] Heading convention…`) sitting above the current milestone does not truncate it either. This now holds for the `state sync` body Progress percent as well as `state json`: `state sync`'s own disk scan is scoped by the same milestone filter under `phase_id_convention: "bracket"`, so the percent it persists into STATE.md agrees with the read path instead of being computed from an unfiltered whole-disk count (a legacy — non-bracket — repo's `state sync` percent is unaffected: that scan stays whole-disk, exactly as before this PR). Regression-proofed by tests/adr-612-bracket-phase-counting.test.cjs. `roadmap analyze` resolves those directories too, so each bracket phase reports its real `disk_status`, `plan_count` and `summary_count` instead of `no_directory` and zeros, and a bracket icebox item listed in the checklist index no longer trips a missing-directory warning from `validate consistency` OR `validate health` — the two verbs now agree on the same ROADMAP instead of one silently excluding the sentinel and the other flagging it. Retired bracket phases leave the denominator, and backlog phases are excluded from every count on a bracket project — both the bracket-sentinel milestones (`[GSD.999]` icebox, `[GSD.00]` pre-milestone) and the engine's reserved `999` phase token, so `roadmap analyze` and `state json` agree there; the one exception is the bare-`0`/`0.x` LEGACY-spelled shape in a bracket repo, where `state json` now counts it (see above) while `roadmap analyze` keeps its historical exclusion — the same analyze/json disagreement the legacy convention already carries today. Every widened read ENGAGES only when the project's resolved `phase_id_convention` is `bracket`, so a project that has not opted in compiles the same patterns it did before and is unaffected. `validate health` additionally gains an advisory W021 with two sub-checks for bracket projects that have opted in: one flags a phase whose bracket milestone disagrees with its enclosing section, the other flags a phase heading still spelled in legacy form that has not yet been migrated to bracket form. The valid values for `phase_id_convention` are documented in `docs/CONFIGURATION.md`; `"bracket"` is a READ-path opt-in until the migrator and write path land. (#2761)
